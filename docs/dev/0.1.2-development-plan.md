# 0.1.2 Development Plan

`0.1.2` is a hardening release that fixes correctness bugs and security leaks
discovered in the `0.1.1` codebase. It does not add new protocol features,
change the public API surface in a breaking way, or alter the security model.

The release stays within the current workspace shape:

- Workspace version: `0.1.1` before the release bump.
- MSRV: Rust `1.95`.
- Selected SSH dependency: `russh 0.60.2`.
- Default features: `client`, `known-hosts`, and `aws-lc-rs`.
- No feature flag additions, removals, or renames.

## Release Goal

Fix all known correctness bugs, security leaks, and API contract violations in
the `0.1.x` line before any new functionality is added. Every fix is
backward-compatible with `0.1.1`. After `0.1.2`, the codebase will be clean
enough to plan `0.2` feature work on a solid foundation.

## How Issues Were Discovered

A full-project audit (`2026-05-15`) examined every source file, every public
type, every `Debug` implementation, every `PartialEq`/`Eq` impl, every error
construction site, every tracing call, and every test. The audit report
identifies:

- 3 security leaks (credentials/cookies visible in `Debug` output).
- 3 data-loss or silent-corruption bugs.
- 5 API contract violations (broken `Eq`, missing `#[non_exhaustive]`, broken
  `Display`).
- 4 small missing pieces of committed-to functionality.
- 5 test categories with insufficient coverage.

## Priority 0: Security Leaks

These items remove credentials and authentication material from `Debug` output.
Every one is a manual `Debug` impl that replaces a `#[derive(Debug)]`.

### 0.1: `X11Params` Debug leaks the X11 cookie

`crates/russh-extra/src/shell.rs:48-49`

`X11Params` derives `Debug`. The `cookie` field is an X11 authentication token,
formatted as a 32-char hex string. The derived `Debug` prints it in plain text.
This transitively affects `Shell`, `ShellBuilder`, `Subsystem`, and
`SubsystemBuilder` Debug output.

Fix: Replace `#[derive(Debug)]` with a manual impl that prints `<redacted>`
for the cookie while showing `single_connection`, `protocol`, and `screen`.

Test: `assert!(!format!("{:?}", params).contains(&params.cookie))`.

### 0.2: `KeyboardInteractiveContext` Debug leaks responses

`crates/russh-extra/src/server.rs:1106`

`KeyboardInteractiveContext` derives `Debug`. The `responses` field is
`Vec<Bytes>` containing the user's typed answers—potentially passwords or 2FA
codes. The derived `Debug` prints all bytes in decimal form.

Fix: Replace `#[derive(Debug)]` with a manual impl that shows
`response_count: usize` and a `responses: <redacted>` marker.

Test: Verify that no response byte value appears in `format!("{:?}", ctx)`.

### 0.3: `X11RequestContext` Debug leaks the auth cookie

`crates/russh-extra/src/server.rs:1529`

`X11RequestContext` derives `Debug`. The `auth_cookie: String` field is an X11
authentication token.

Fix: Manual `Debug` impl that shows `session_id`, `channel_id`, and
`auth_cookie: <redacted>`.

Test: `assert!(!format!("{:?}", ctx).contains(&ctx.auth_cookie))`.

Acceptance (Priority 0):

- No derived `Debug` on any type containing an X11 cookie or user input
  that may include credentials.
- Each fix has a test that asserts the sensitive field is not present in
  the formatted output.

## Priority 1: Data Loss and Silent Corruption

These bugs cause real user-visible data loss or incorrect behavior at runtime.

### 1.1: `ShellAsyncIo` silently drops stderr data

`crates/russh-extra/src/shell.rs:897`

The `run_channel_bridge` task uses `_ => {}` as a catch-all in a
`tokio::select!` branch. `ChannelMsg::ExtendedData` (stderr) matches this arm
and the data is silently discarded. Users of `ShellAsyncIo` cannot receive
stderr through the `AsyncRead` impl.

Fix: Add a second unbounded mpsc channel (`stderr_tx`/`stderr_rx`) to the
bridge. Route `ExtendedData` to `stderr_tx`. Expose stderr through a new
`stderr_rx` field on `ShellAsyncIo`—or merge stderr into the existing
`read_rx` channel (interleaved, matching `ShellHandle::read()` behavior).

Decision point: Interleaving stdout and stderr matches `ShellHandle` behavior
and avoids a second API surface. A separate `stderr_rx` path is a strictly
more capable API but requires design work. **Prefer interleaving** for 0.1.2
to keep scope minimal; a separate stream can be added later if users request
it.

Test: Open a shell on the loopback server that writes to stderr. Verify
`ShellAsyncIo::read()` returns stderr bytes.

### 1.2: `ShellAsyncIo` bridge task never exits on drop

`crates/russh-extra/src/shell.rs:252, 874`

When constructing `ShellAsyncIo`, `cmd_tx` is cloned into `_cmd_tx` and passed
to `run_channel_bridge`. The bridge task holds a sender to its own command
channel, so `cmd_rx.recv()` never returns `None`—even after `ShellAsyncIo` is
dropped and the original `cmd_tx` is gone. The bridge task lives forever until
the server closes the SSH channel or sends data that triggers
`read_tx.send()` failure.

Fix: Remove the `_cmd_tx` clone. The bridge task should not hold a sender to
its own control channel. When `ShellAsyncIo` is dropped, `cmd_rx.recv()`
returns `None` and the bridge task exits cleanly.

Test: Drop `ShellAsyncIo` without calling close. Verify the bridge task exits
within a bounded time (e.g., by observing that `channel.close()` is received
by the loopback server).

### 1.3: `KnownHosts::check()` short-circuits on the first mismatching entry

`crates/russh-extra/src/known_hosts.rs:261`

When an entry matches the hostname but its key bytes differ, `check()`
immediately returns `Changed`. Subsequent entries for the same host (e.g., a
second entry with a different key type) are never examined. This means a user
with both `ssh-ed25519` and `ssh-rsa` entries for the same host will get a
spurious `Changed` result if the server presents the second key type.

Fix: Instead of returning `Changed` on the first key-byte mismatch, continue
scanning. Track two states: `saw_candidate_match: Option<&KnownHostsEntry>` for
the most recent candidate (hostname+port matches, not revoked, key matches),
and `saw_mismatch: bool` for any hostname+port match where the key did not
match. After the loop:
- If `saw_candidate_match` is set, return `Match`.
- If `saw_mismatch` is set but no candidate matched, return `Changed`.
- Otherwise return `NotFound`.

`@revoked` entries remain a short-circuit: encountering a revoked matching
entry still returns `Revoked` immediately (correct behavior).

Test: Create a store with two entries for the same host (different key types).
Verify that connecting with the second key type returns `Match`, not `Changed`.

Acceptance (Priority 1):

- `ShellAsyncIo` no longer drops stderr.
- `ShellAsyncIo` bridge task exits when `ShellAsyncIo` is dropped.
- `KnownHosts::check()` finds a matching key among multiple entries for the
  same host.
- No existing test regresses.

## Priority 2: API Contract Violations

These items fix public API behavior that contradicts documented contracts or
reasonable user expectations. All are backward-compatible for users following
the documented API (constructors, not struct literals), with one minor caveat:
adding `#[non_exhaustive]` to `TcpEndpoint` and `StreamLocalSpec` (items 2.4)
will break struct-literal construction of those types. That is acceptable in
`0.x` and consistent with every other comparable type in the crate (all of
which already carry `#[non_exhaustive]`).

### 2.1: `ClientConfig::Eq` broken for keyboard-interactive credentials

`crates/russh-extra-core/src/auth.rs:288` and `config.rs:82`

`Credential::PartialEq` returns `false` for all `KeyboardInteractive`
comparisons. Since `ClientConfig` derives `Eq` (via `#[derive]` on config.rs
line 82), two `ClientConfig` values that differ only in keyboard-interactive
handler closures will never compare equal. Worse, two configs that are
*identical in every meaningful way* but happen to contain
`Credential::KeyboardInteractive` will also compare unequal.

Fix: Change `(Self::KeyboardInteractive(_), Self::KeyboardInteractive(_))`
from `false` to `true`. Two keyboard-interactive credentials are equal for
config-comparison purposes because they represent the same auth method; the
closures themselves are not comparable and `Eq` on closures is a category
error anyway. The alternative (removing `Eq` from `ClientConfig` entirely) is
more correct in the abstract but would be a breaking change to downstream code
that currently uses `assert_eq!` on configs; defer that to 0.2 if needed.

Test: Two `ClientConfig` values with keyboard-interactive credentials must
compare equal when all other fields match.

### 2.2: `set_strict_host_key_checking(bool)` destroys `PinnedSha256`

`crates/russh-extra-core/src/config.rs:167-173`

`set_strict_host_key_checking` unconditionally sets `host_key_policy` to
`Strict` or `InsecureAcceptAny`, discarding any `PinnedSha256` fingerprints
that were previously configured. This is a silent data loss bug.

Fix: Deprecate `set_strict_host_key_checking` and replace it with a doc that
points users to `set_host_key_policy`. Alternatively, make the method a no-op
when the current policy is `PinnedSha256` and log a warning. **Prefer
deprecation** because the method's name is a boolean toggle that cannot
express the three states (strict/insecure/pinned) available to users.

Add `#[deprecated = "use set_host_key_policy instead"]` and keep the body
for backward compatibility.

Test: Set `PinnedSha256`, call `set_strict_host_key_checking(true)`, verify
`PinnedSha256` is preserved (old code would have lost it, deprecation means
we just warn). Or: call the deprecated method, verify it still compiles.

### 2.3: `Pty` missing `#[non_exhaustive]`

`crates/russh-extra-core/src/channel.rs:127`

`Pty` is a public struct with private fields, but it is **not** marked
`#[non_exhaustive]`. This means no new fields can be added to `Pty` in the
future without a breaking change. Compare with `CommandLimits`, `ChannelKind`,
`CommandExit`, `HostKeyFingerprint`, `ClientConfig`, `ServerConfig`, `Timeouts`,
and `Keepalive`—all of which are `#[non_exhaustive]`.

Fix: Add `#[non_exhaustive]` to the struct. This is backward-compatible for
`0.x` because `Pty` has private fields and is constructed via `Pty::new()`.
Users cannot construct it with struct literal syntax.

Test: Verify `Pty` is `#[non_exhaustive]` via compile-fail or by checking
the attribute.

### 2.4: `TcpEndpoint` and `StreamLocalSpec` missing `#[non_exhaustive]`

`crates/russh-extra-core/src/forward.rs:18, 58`

Same issue as `Pty`. Both structs have all-public fields and are constructed
via `new()` methods. They are not `#[non_exhaustive]`, locking their field
sets.

Fix: Add `#[non_exhaustive]` to both structs. Since fields are `pub`,
constructing them with struct literal syntax will become a compile error.
This is acceptable in `0.x` and the `new()` constructors continue to work.

Test: Verify both structs carry the attribute.

### 2.5: `Endpoint::Display` breaks IPv6 round-trip

`crates/russh-extra-core/src/session.rs:68-70`

`Display` for `Endpoint` formats as `host:port`. For IPv6 addresses like
`2001:db8::1`, this produces `2001:db8::1:22`—a string that is ambiguous
and cannot be parsed back. The `authority()` method correctly handles this
with bracket notation `[2001:db8::1]:22`.

Fix: Change `Display` to delegate to `authority()`:

```rust
impl fmt::Display for Endpoint {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        f.write_str(&self.authority())
    }
}
```

This is a minor behavioral change (users who `println!("{}", ep)` will now
see `[::1]:22` instead of `::1:22`). In practice the old format was already
broken for IPv6, so this is a bug fix, not a feature change.

Test: `Endpoint::parse("[::1]:22").unwrap().to_string()` must produce
`"[::1]:22"`, and re-parsing that string must return the same `Endpoint`.

Acceptance (Priority 2):

- `ClientConfig` with keyboard-interactive credentials compares correctly.
- `set_strict_host_key_checking` is deprecated without data loss.
- `Pty`, `TcpEndpoint`, and `StreamLocalSpec` are `#[non_exhaustive]`.
- `Endpoint::Display` produces a parseable authority string for both IPv4
  and IPv6.
- All existing tests pass.

## Priority 3: Small Missing Functionality

These items add small, self-contained pieces of functionality that are either
committed to in AGENTS.md or expected by users of the existing API. None
requires new design work or feature flags.

### 3.1: `CommandOutput::check_success(self) -> Result<Self>`

`crates/russh-extra/src/client.rs:1813-1827`

AGENTS.md section 11 specifies `check_success(self) -> Result<Self>` on
`CommandOutput`. Only `success() -> bool` exists. The `Error::CommandExit`
variant already exists in the error taxonomy (`error.rs:301`) but is never
constructed.

Fix: Add `check_success()`. Wire the `CommandExit` error variant, which already
exists in `russh-extra-core` but has never been constructed at runtime:

```rust
impl CommandOutput {
    pub fn check_success(self) -> Result<Self> {
        if self.exit.success() {
            Ok(self)
        } else {
            Err(Error::command_exit(self.exit))
        }
    }
}
```

Test: `CommandOutput` with exit 0 passes `check_success`. With exit 42,
`check_success` returns `Err(Error::CommandExit(...))`. With `Missing` exit
status, `check_success` also returns an error.

### 3.2: `Identity::key_file()` does not expand tilde

`crates/russh-extra-core/src/auth.rs:127-132`

`Identity::key_file("~/.ssh/id_rsa")` stores the literal `~/` path. The
`load_openssh_file()` convenience method does expand tilde, but a user who
constructs `Identity::key_file()` and passes it to `ClientBuilder::identity()`
expects the same behavior.

Fix: Call `expand_tilde()` inside `key_file()` before storing the path.

Test: Create `Identity::key_file("~/nonexistent")`, verify the stored path
does not start with `~`. (The existing `expand_tilde()` function reads
`$HOME`; test with a known temp dir.)

### 3.3: `TerminalMode` missing common SSH terminal modes

`crates/russh-extra-core/src/channel.rs:203-219`

The current `TerminalMode` enum has 7 named variants plus `Custom(u8)`.
SSH RFC 4254 section 8 defines approximately 20 terminal modes. Common
missing modes include `ECHO`, `ECHOE`, `ECHOK`, `ECHONL`, `ICANON`, `ISIG`,
`ICRNL`, `INLCR`, `IGNCR`, `OPOST`, `ONLCR`, `OCRNL`, and `ONLRET`.

Fix: Add the missing named variants. Keep `Custom(u8)` for unknown opcodes.
Update `terminal_mode_to_pty()` in `shell.rs` to map each new variant to the
corresponding `russh::Pty` variant (using the SSH protocol opcodes defined in
the `russh` crate, not the RFC numbers directly). The enum is
`#[non_exhaustive]`, so adding variants is backward-compatible.

Test: Verify each new variant constructs and maps correctly (round-trip
through `with_mode` / `build_terminal_modes`).

### 3.4: Known-hosts comma-separated hostnames only store the first

`crates/russh-extra/src/known_hosts.rs:127-131`

`parse_host_pattern` returns `Option<(String, u16)>`. When the pattern
contains commas (e.g. `host-a,host-b,host-c`), it splits on `,` but only
takes `parts.first()`, discarding all subsequent hosts. A `known_hosts`
line like `host-a,host-b,host-c ssh-ed25519 AAA...` creates an entry only
for `host-a`; `host-b` and `host-c` are silently lost.

Fix: Change `parse_host_pattern` to return `Vec<(String, u16)>` instead of
`Option<(String, u16)>`. Change `KnownHostsEntry::parse` to return
`Vec<KnownHostsEntry>` instead of `Option<Self>`. Update
`parse_known_hosts_content` to call `extend` instead of `push`. Creating
multiple single-host entries is simpler than extending `KnownHostsEntry` to
hold a `Vec` of hostnames. The `add_entry` method already deduplicates by
host+port.

Test: Parse a line with three comma-separated hosts. Verify three entries
exist in the store, all with the same key and all matching their respective
hostnames.

Acceptance (Priority 3):

- `CommandOutput::check_success()` exists and is tested.
- `Identity::key_file()` expands tilde.
- `TerminalMode` covers common SSH modes with correct opcodes.
- Comma-separated `known_hosts` lines produce one entry per host.

## Priority 4: Test Hardening

These items add tests for existing behavior. No runtime code changes are
planned in this round; any bugs discovered during test writing are fixed in
a follow-up round.

### 4.1: Debug leak tests for production types

Add tests that verify `Debug` output does not contain:

- `Identity` private key data (assert `<N bytes redacted>` in output).
- `Password` content (assert `Password(***)` in output).
- `ServerHostKey` private key data (assert `***` in output).
- `Credential::Password` content (assert redaction).
- `ClientConfig` does not expose credential details.

These tests exist for `LoopbackServerConfig` (test-support only) but not for
production types.

### 4.2: Complete `SftpServerHandler` method coverage

`tests/tests/sftp_server.rs` tests 5 of 19 `SftpServerHandler` methods. Add
tests for the remaining 14:

`create`, `readdir`, `write` at non-zero offset, `setstat`, `fsetstat`,
`mkdir`, `rmdir`, `rename`, `symlink`, `readlink`, `canonicalize`, `fstat`,
`opendir` (independent verification), `lstat` (independent verification).

Each test: configure `InMemorySftpHandler` to implement the method, connect
a real `SftpClient`, exercise the operation, verify the result.

### 4.3: Known-hosts edge case tests

Add tests for:

- Malformed line mixed with valid entries (parser recovers, warning collected).
- Empty `known_hosts` file (no panic, `NotFound` for any host).
- Line with invalid base64 (warning collected, entry skipped).
- Line with fewer than 3 whitespace-separated fields (warning collected).
- `KnownHostsEntry::Debug` does not expose anything secret (public keys are
  not secrets; verify the output is structured correctly).
- Port-specific entry `[host]:2222` matched only when port 2222 is requested.
- Non-22 port entry saved with `[host]:port` format.

### 4.4: Large data tests

- Command output at 8 MiB (the default `CommandLimits`): verify no truncation.
- Command output at `limit + 1` bytes: verify `ChannelErrorKind::Read` error.
- SFTP read at exactly 32 KiB: verify complete read.
- SFTP read at 64 KiB: verify two reads return correctly or the implementation
  handles chunking.
- Tunnel stream large bidirectional transfer (1 MiB each direction).

### 4.5: ShellAsyncIo lifecycle tests

- Drop `ShellAsyncIo` without calling close: verify channel is closed.
- Call `close()` on `ShellHandle` then drop `ShellAsyncIo`: verify no
  double-close error.
- Stderr forwarding through `ShellAsyncIo` (paired with Priority 1.1 fix).

Acceptance (Priority 4):

- All new tests pass under `cargo test --workspace --all-features`.
- Test count increases measurably from the 0.1.1 baseline (~217).

## Out of Scope for 0.1.2

These are valid project goals that belong in `0.2` or later:

- Hashed known-hosts matching or writing (`|1|...` entries).
- Wildcard known-hosts matching (`*.example.com`).
- Dynamic SOCKS-style forwarding.
- SFTP v4+ protocol extensions or OpenSSH SFTP extensions.
- `FXP_EXTENDED` support.
- Tracing instrumentation overhaul (every module has gaps; this is a dedicated
  project).
- `open_sessions` synchronization fix for server handler clones (requires
  structural refactoring of `HighLevelRusshHandler`).
- Command execution timeout (requires new `Timeouts` field and loop changes).
- `zeroize` integration for `Password` and private keys (new dependency).
- Removing unused error kind variants (breaking change).
- Adding `From<Username> for String` or other convenience conversions.
- `CommandExit::Signal` `core_dumped` field.
- `ChannelKind` X11 and AuthAgent variants.
- `Keepalive` runtime implementation (configuration exists but is not wired).
- No-concurrency-limit on local forwarding accept loop (current behavior is
  documented; adding a semaphore is a feature, not a bug fix).
- Removing `Eq` from `ClientConfig` entirely (the Priority 2.1 fix changes
  the `Credential::PartialEq` behavior; removing `Eq` from the config struct is
  more correct but would be a breaking change — save for 0.2).
- `TcpEndpoint` / `StreamLocalSpec` `FromStr`, `Display`, and tilde expansion.
- `Pty::with_term()` setter.


past the gate unless explicitly noted in an audit finding.
